# TikTok 视频链接自动补全

按「账号 + 标题 + 发布日期」自动找回 TikTok 视频链接，并**直接回填到飞书多维表格**。

---

## 它解决什么问题

你有一张表，记录了每个账号发布了什么内容（标题、日期），但**链接要一条条手动去翻**。
这个程序每天自动跑一次，把链接补齐写回原表。

---

## 表格地址

**飞书多维表格：TikTok 视频链接管理**

> 出于脱敏，仓库里不写具体地址。表格链接请从本机 `config.json` 的 `feishu.url` 取值，
> 形如 `https://<租户域名>.feishu.cn/base/<BASE_TOKEN>?table=<TABLE_ID>`：
> `/base/` 后面那段是 `FEISHU_BASE_TOKEN`，`table=` 后面那段是 `FEISHU_TABLE_ID`。

表结构（表名「视频链接补全」）：

| 字段 | 类型 | 谁来填 |
|---|---|---|
| TikTok账号 | 文本 | **你填** — `@xxx` 或账号名或主页链接都行 |
| 视频标题 | 文本 | **你填** — 不需要和 TikTok 上完全一致，写句子片段也能匹配 |
| 发布日期 | 日期 | **你填** — 表里直接选日期即可，**按北京时间记**（与抓取端一致） |
| TikTok链接 | 链接 | 程序自动回填 |
| 视频ID | 公式 | 自动 — 从「TikTok链接」里抽 19 位视频 ID，可用来肉眼核对 |
| 播放量 | 数字 | 程序自动回填 — 每 30 分钟自动刷新（`--refresh-stats` 模式） |
| 点赞数 | 数字 | 程序自动回填 — 每 30 分钟自动刷新（`--refresh-stats` 模式） |
| 状态 | 单选 | 程序自动回填（待补全 / 已补全 / 需人工确认 / 未找到） |
| 匹配到的标题 | 文本 | 程序自动回填 — TikTok 上真实的视频描述，用来肉眼核对 |
| 提示 | 文本 | 程序自动回填 — 置信度、未匹配原因 |
| **同步触发** | 文本 | **你不用管** — 由「立即同步」按钮写入；守护进程读取后自动清空 |
| **立即同步** | 按钮 | **你点** — 点击后立刻触发同步该行（≤ 60 秒），链接和播放量/点赞数一起更新 |

**你只需要每天把新增视频的「账号 / 标题 / 发布日期」三列粘进去，剩下的交给程序。**

## 用法

### 方式一：飞书表格模式（推荐）

```bash
# 直接双击这个文件
run-feishu.bat

# 或命令行
node src/sync.cjs --source feishu
```

程序会：读表 → 找出「链接为空且状态不是已补全」的记录 → 抓 TikTok → 匹配 → 写回原表。

```bash
# 先看看会填什么，不真的改表
node src/sync.cjs --source feishu --dry-run

# 用本地缓存跑，秒级完成（调试用；正式跑不要加，会拿不到最新视频）
node src/sync.cjs --source feishu --use-cache

# 重试所有「未找到」的记录（默认它们是终态、不再重抓）
node src/sync.cjs --source feishu --retry

# 连已有链接的记录也重新校验一遍
node src/sync.cjs --source feishu --force

# 只处理某个账号
node src/sync.cjs --source feishu --account brand_mx

# 只刷新已有链接行的播放量/点赞数（不动链接、状态）
node src/sync.cjs --source feishu --refresh-stats

# 强制立刻刷一次 stats（绕过 25 分钟最小间隔闸门）
node src/sync.cjs --source feishu --refresh-stats --force
```

### 方式二：本地 CSV 模式

不想动飞书表时可用，输入输出都是本地文件（见 `data/input.csv`）。

```bash
node src/sync.cjs --input data/input.csv --output data/output.csv
```

## 触发同步

三种方式，可同时开着（互不打架）：

### 1) 在表格里点「立即同步」按钮（最快，≤ 60 秒）

每行末尾都有 **「立即同步」按钮**，点击后：
- 飞书工作流把该行的「同步触发」字段写成 `TRIGGER <时间戳>`
- 本地守护进程（每 60 秒扫一次）看到标记就立刻跑 sync.cjs
- 处理完成后自动清掉标记，状态/链接照常更新

> 这一套**绕过飞书 RRULE 最密 5 分钟的限制**，把响应速度压到 ≤ 60 秒。

### 2) 双击 `run-feishu.bat`（手动）

填完一批数据后双击，几秒内就开始抓取并回填。
对应命令：`node src/sync.cjs --source feishu`

### 3) 定时任务（每 5 分钟兜底）

已配置定时任务，每 5 分钟扫一次表里新增的待补记录。
**只有当表里有「状态为空或待补全」的新记录时**才会启动浏览器抓取；空跑时不会打扰你。
对应命令：`node src/sync.cjs --source feishu`

> 想让某条「未找到 / 需人工确认」记录再试一次：要么点该行的「立即同步」按钮，要么把状态改回「待补全」再等下一轮定时任务。命令行可以加 `--retry` 强制重试所有「未找到」记录。

### 4) 播放量 / 点赞数自动刷新（每 30 分钟）

「立即同步」按钮和 5 分钟定时任务都只处理**还没补上链接**的行；已经补全的行属于终态，
默认永远不会被重新抓取 —— 所以早期版本里，播放量/点赞数只有手动点按钮才会更新。

现在用 `--refresh-stats` 模式补上这一块：

```bash
node src/sync.cjs --source feishu --refresh-stats   # 只刷播放量/点赞数
```

它做的事很克制：

| 项 | 行为 |
|---|---|
| 处理范围 | 只处理**已经有 TikTok 链接**的行（已补全 / 需人工确认） |
| 匹配方式 | 用链接里的 **19 位视频 ID** 去抓取结果里精确查表（不用标题模糊匹配，杜绝张冠李戴） |
| 写入字段 | **只有「播放量」「点赞数」**；链接、状态、匹配到的标题、置信度、按钮标记一律不动 |
| 抓不到时 | 该行**保持原值不变**（不会被清零），等下一轮再刷 |
| 限流保护 | 某账号抓到 0 条 → 隔 10 秒自动重试一次；仍为 0 则跳过该账号并打印「命中率偏低」提示 |
| 缓存保护 | 降级抓取（0 条 / 比上次少）不会覆盖已有的 `data/cache/*.json` |

**谁来触发它**（两条路，互为兜底，靠 `data/stats-refresh.json` 的「最小间隔 25 分钟」闸门去重，
所以不会出现每 15 分钟抓一次把 TikTok 抓出限流的情况）：

1. **本地守护进程**：每 30 轮（≈30 分钟）自动多跑一次 `--refresh-stats`，纯本地，不依赖任何云端服务
2. **定时任务**「TikTok 播放量/点赞数定时刷新（每30分钟）」：每天 0/30 分各跑一次，作为守护进程挂掉时的兜底

> 想立刻刷一次：`node src/sync.cjs --source feishu --refresh-stats --force`（`--force` 用来绕过 25 分钟闸门）

### 5) 云端托管：不依赖自己的电脑（GitHub Actions）

上面 1~4 条的所有调度**都跑在本机**（包括那两个「WorkBuddy 定时任务」——它们由本机客户端执行，
不是飞书云上的），所以本机关机 / 断网 / 休眠就全都停了。

想把整条链路搬到云端，做到「关机也不影响、换任何电脑都能操作」：

```bash
node bin/smoke-test.cjs          # 先验证：出口 IP / TikTok 可达 / 飞书权限 / 真抓一次
node bin/smoke-test.cjs --skip-crawl   # 只测网络与飞书（秒级）
```

完整部署步骤见 **[DEPLOY-GITHUB.md](DEPLOY-GITHUB.md)**。要点速览：

| 项 | 说明 |
|---|---|
| 运行位置 | GitHub Actions（ubuntu runner），每 30 分钟一轮 + 可手动触发 |
| 飞书写入身份 | bot（`tenant_access_token`，2 小时自动续期，**不会像 OAuth 那样约 7 天后过期**） |
| 硬门槛 | GitHub 机房 IP 能不能访问 TikTok —— 用 `smoke-only` 模式先测，不通就得配代理 |
| 唯一免费前提 | 仓库设为 **public**（私有仓库 2000 分钟/月不够用，本方案约需 2880 分钟） |
| 响应延迟 | 按钮从「≤60 秒」变成「≤30 分钟」（云端最密只能到这个粒度） |
| 上云后 | `npm run watch:stop` 停掉本机守护进程，避免两边重复抓取（文件锁只在同一台机器生效） |

### 守护进程：让按钮真正"立刻"

定时任务最密只能设到 5 分钟（飞书平台硬性限制），所以光靠定时任务，按钮至少要等 5 分钟才会被处理。
要 ≤ 60 秒响应，**必须额外跑一个本地守护进程**：

```bash
npm run watch:start    # 后台启动（推荐，常驻）
npm run watch:stop     # 结束守护进程（写 data/watch.disabled，看门狗不再自动拉起）
npm run watch:restart  # 重启
npm run watch:status   # 一键自检：全自动链路现在通不通
npm run watch          # 前台跑（Ctrl+C 退出，看日志用）
```

> 守护进程每隔 60 秒 spawn 一次 `sync.cjs`（找链接），每 30 轮额外多跑一次 `--refresh-stats`（刷播放量/点赞数）。
> 关闭窗口也不会停；不需要时 `npm run watch:stop` 停掉，按钮就退化为「等下一次定时任务」（≤ 5 分钟）。
> 自定义节奏：`node src/watch-trigger.cjs --stats-every 15`（每 15 轮刷一次 stats）。

### 自愈能力（这块决定了能不能真的"全自动"）

跑久了必然会遇到：上一轮 sync 被中断/崩溃、进程被杀、机器休眠。这些情况以前会让自动同步
**静默停摆**（锁清不掉 → 后续每一轮都被挡住空转），现在都能自愈：

| 故障 | 现在的表现 |
|---|---|
| sync.cjs 异常退出留下 `data/sync.lock` | 锁里记录了持有者 PID。下一轮抢锁时用 signal 0 探测该进程，**发现已死就立刻接管**（不再像旧版那样干等 10 分钟） |
| 进程被杀 / Ctrl+C | 退出前主动清锁；即使没清掉，上面那条也会兜住 |
| 锁真的删不掉（Windows 句柄未释放） | 日志打印「旧锁文件删除失败」，改为**原地覆写**锁内容继续跑 |
| 持锁进程假死（PID 还在但不干活） | 持锁超过 15 分钟 → 强制接管 |
| 守护进程自己死了 | 看门狗（`bin/watchdog.vbs`）每 30s 检查**心跳文件** `data/watch.heartbeat`，超过 3 分钟没更新就重新拉起 |
| 守护进程被重复启动 | `data/watch.epoch` 世代号：新守护进程起来后，旧的在下一轮自动退休，不会留下孤儿进程 |
| 开机忘启动 | `bin/autostart.bat` 已放进「启动」文件夹，登录即拉起看门狗 |
| TikTok 限流（抓到 0 条） | 隔 10 秒自动重试一次；仍失败则跳过该账号，**已写入的数值保持原值不变**（不会被清零/覆盖），下一轮自动补上 |
| 降级抓取把好缓存冲掉 | 抓到的条数为 0 或比上次少时，**不覆盖** `data/cache/*.json` |
| 点按钮/强制重跑时正好撞上限流 | 该账号本轮抓取降级的行**整行跳过不写**（不会把「已补全」误降级成「未找到」），TRIGGER 标记保留，下一轮自动重试 |
| 临时文件堆积（进程被 kill 后残留） | 每轮启动时清理超过 1 小时的 `data/tmp-write-*.json` |

随时用 `npm run watch:status` 体检，输出大概长这样：

```
[OK]   守护进程心跳正常：PID=29608，42s 前刚报活（已完成第 3 轮）
[OK]   watch.pid=29608 进程存活
[OK]   没有残留的 sync.lock
[OK]   历史上一共自愈接管僵尸锁 6 次（说明锁机制在工作）
[OK]   开机自启脚本已安装（启动文件夹）
```

> 三类触发（本地守护进程找链接、定时任务找链接、stats 刷新）会同时调 `sync.cjs`，
> 靠文件锁互斥，不会重复抓同一行。定时任务的作用是「守护进程挂了时的兜底」；
> stats 刷新另有 25 分钟「最小间隔」闸门，避免本地和云端两条路重复抓 TikTok。

## 状态说明

飞书表里的「状态」列：

| 状态 | 含义 | 你该做什么 |
|---|---|---|
| 待补全 | 刚粘进去，还没跑 | 等定时任务跑 / 双击 `run-feishu.bat` |
| 已补全 | 置信度 ≥ 0.85，链接已写入 | 直接用 |
| 需人工确认 | 置信度 0.65~0.85，或「当天该账号仅此一条视频」的日期兜底 | 扫一眼「匹配到的标题」列确认 |
| 未找到 | 没有可靠候选，**链接留空** | 看「提示」列排查；想重试就把状态改回「待补全」 |

> 「已补全 / 需人工确认 / 未找到」**都是终态**，定时任务不会反复重抓。
> 想让某条记录再试一次，**点该行末尾的「立即同步」按钮**（≤ 60 秒生效），或把状态改回「待补全」。
> 命令行也可以加 `--retry` 强制重试所有「未找到」记录。

## 匹配原理（为什么能做到）

1. 打开账号主页，**拦截 TikTok 自身的 `item_list` 接口响应** —— 直接拿到结构化的
   `视频ID / 描述 / 发布时间戳`，比爬页面 DOM 精确得多。
2. 标题做三路打分：
   - 字符 bigram 相似度 —— 抗语序变化
   - 词级覆盖率 —— 抗长度差异
   - 包含关系 —— 你只写了片段也能命中
3. 叠加「发布日期」加权（标题 0.72 + 日期 0.28；同天满分，允许差 1 天以吸收时区误差）。
4. **全局唯一分配**：一条视频只会分配给一条记录，避免同一账号多条记录抢同一个链接。
5. 自动剥离 TikTok 追加的音频署名、话题标签、@提及、emoji 后再比对。
6. 没有可靠候选时，会给出具体原因（未抓到视频 / 当天有多条但标题都不像 / 日期超范围）。

## 配置

`config.json`（本机用；**已加入 `.gitignore`，不入库**）：

| 项 | 说明 |
|---|---|
| `proxy` | 代理地址。**本机必须走代理才能访问 TikTok**，务必按实际情况填 |
| `chromePath` | 使用的 Chrome 可执行文件 |
| `timezone` | 抓取的「发布日期」判定时区，**默认北京时间 `Asia/Shanghai`**——你填表里的日期按北京时间记录即可 |
| `maxScroll` | 主页滚动次数，决定每个账号抓多少条视频（默认约 40~50 条） |
| `matchThreshold` | 匹配阈值，调低=更激进，调高=更严格 |
| `columns` | CSV 模式的表头列名映射 |
| `feishu` | 飞书表坐标（baseToken / tableId / 字段名 / 状态选项） |
| `feishu.appId` / `appSecret` | 可选。配了就自动切到 openapi（bot）后端，不配则用本机 lark-cli |

> 记录跨度较大时，把 `maxScroll` 调大（例如 20）以覆盖更早的视频。
> 换一张飞书表：改 `config.json` 里的 `feishu.baseToken` 和 `feishu.tableId` 即可。

`config.ci.json`（云端用；**入库，不含任何凭证**）：只有运行参数和字段映射，
表格坐标与 app 凭证全部走环境变量，避免密钥进仓库。

支持的环境变量（全部可选，适合 CI / 服务器）：

| 变量 | 作用 |
|---|---|
| `FEISHU_APP_ID` / `FEISHU_APP_SECRET` | 应用凭证。设了就切到 openapi（bot）后端 |
| `FEISHU_BACKEND` | 强制指定后端：`openapi` 或 `lark-cli` |
| `FEISHU_BASE_TOKEN` / `FEISHU_TABLE_ID` / `FEISHU_URL` | 覆盖表格坐标 |
| `TIKTOK_PROXY` | 抓取代理（覆盖 config 里的 proxy） |
| `CHROME_PATH` / `TIKTOK_CHROME_PATH` | Chrome 路径；路径不存在时交给 playwright 自己找（Linux runner 靠这个） |
| `TZ` | 容器时区，云端建议设 `Asia/Shanghai` |

## 常见问题

**Q: 提示「该账号未抓到任何视频」**
账号名拼错了，或该账号主页非公开。

**Q: 大面积「未找到」**
先看 `data/cache/<账号>.json` 里是否真有视频。若有，说明标题差异过大 ——
把标题写得更接近视频描述，或调低 `matchThreshold`。

**Q: 「视频标题」可以写中文备注吗？**
标题列**必须是你想匹配的那条视频的标题（或其中一段文字）**。
如果写的是中文备注、而视频描述是西班牙语，标题就匹配不上了 ——
这时只能靠「发布日期」兜底（该账号当天只有一条视频时才会命中）。
建议直接把视频标题贴进来。

**Q: 想抓更多历史视频**
调大 `config.json` 里的 `maxScroll`。

**Q: 会不会抓错链接？**
不会静默给错。低置信度不自动写链接，会明确标成「需人工确认 / 未找到」并给出原因。

**Q: 程序报 lark-cli 授权相关错误**
飞书登录态会过期（约 7 天）。重新连一次飞书即可。

**Q: 按钮、定时任务、守护进程同时跑，会重复抓同一行吗？**
不会。`sync.cjs` 用 `data/sync.lock` 文件锁保证同一时间只有一个进程在跑；且每次跑完都会清掉触发标记 + 把状态置为终态，下一轮自动跳过。三个触发器共用同一个 `sync.cjs`，行为完全一致。

**Q: 「立即同步」按钮不生效 / 点了没反应**
1. 看 `data/watch.log` 末尾几行 —— 守护进程是否在跑（`npm run watch:start` 启动过吗？）
2. 看表里该行的「同步触发」字段 —— 是否被清掉了？被清掉说明跑过；没清说明守护进程没看到
3. 看 `data/sync.lock` 是否残留 —— 现在锁里会写持有者 PID，`sync.cjs` 每次抢锁都会探测该 PID 是否还活着：
   - 持有者已死 → 立刻接管，不用人工清理
   - 持有者还活着 → 正常跳过（说明真有一轮在跑）
   - 持锁超过 15 分钟仍存活 → 判定假死，强制接管
   - 被 `kill` / `Ctrl+C` 时也会在退出前主动清锁
   也就是说**僵尸锁已经能自愈，不需要再手动删**；只有日志里持续出现「接管锁」且伴随异常才算真问题
